# Unified AD5X plugin: bambufy + lessWaste + QuickSwap

Status: design approved (approach A) — 2026-09-19
Project name: **chromaswap**
Scope of this spec: **Phase 1 in full; Phase 2 as direction + open questions** (Phase 2 gets its own spec).

## Goal

One Z-Mod plugin for the Flashforge AD5X that combines:

- **bambufy** (function3d) — slicer-controlled purge, Bambu Studio + Orca, color mapping, backup, recovery.
- **lessWaste** (Hrybmo, fork of bambufy 1.2.10) — channel swap, virtual channels, S_PURGE / L_PURGE / smart purge, IFS unlock.
- **QuickSwap** (ninjamida, MIT) — fast color change (async IFS commands, parallel moves) and calibrations.
- **nopoop** — out of scope. It is now Z-Mod core; the plugin is a 2-line stub.

## Constraints

- Must be tested by the user on a real AD5X before Phase 2 is called done (cutter/unload sequence).
- User intends to **publish later**. bambufy and lessWaste have no LICENSE file; written permission from function3d and Hrybmo is needed before publishing. QuickSwap is MIT (keep copyright notice). Keep per-file credits.
- Preserve the existing plugin mechanics: `install.sh`/`uninstall.sh`, per-language `<lang>/*.cfg` generated by the translate scripts, `preprint.py`, `restore_gcode.sh`.
- Sources: `bambufy` HEAD (`fdacbbd`), tag `v1.2.10` (merge base), `lessWaste` HEAD.

## Measured facts (from a dry run)

- Merge base bambufy `v1.2.10` → lessWaste: **1085 changed lines** (after normalising CRLF and variable prefix).
- Merge base → bambufy HEAD: **1039 changed lines**, 49 commits.
- `git merge-file` 3-way (lessWaste ← base → bambufy HEAD) on `en/*.cfg`: **46 conflict hunks**. Tractable, but not mechanical.
- Macro sets: 87 in common; bambufy-only and lessWaste-only lists are in the analysis (color auto-assign / port-type dialog / G28 sequence vs. channel swap / line & smart purge / unlock IFS).
- QuickSwap depends on Z-Mod through a **narrow** surface: `zmod_ifs.get_prutok_config()` (~10 per-filament keys from `filament.json`), `zmod_ifs.get_extruder_sensor`, `zmod_ifs.ifs_data.*`, `get_current_channel_from_config`, the `_command`/`_command_lock` IFS channel, plus a few Klipper objects. `zmod_ifs` (Python) keeps running under bambufy, so most of this may keep working unchanged.

## Phase 1 — bambufy + lessWaste

**Approach:** start from bambufy HEAD; apply the lessWaste delta (base `v1.2.10` → lessWaste) as a 3-way merge.

1. Normalise: strip CRLF, rename variable prefixes `less_waste_*` / `bambufy_*` → one unified prefix. Pick the plugin name/prefix at implementation start (open item below).
2. Generate the merged `en` config with `git merge-file`; resolve the 46 hunks by hand. Rules:
   - Bug fixes from bambufy HEAD win over the old base.
   - lessWaste features become **options in `_IFS_VARS`** (channel swap, virtual channels, S_PURGE/L_PURGE/smart purge, unlock-IFS-after-boot), default off where they change stock bambufy behaviour.
   - Where both rewrote the same macro (`PAUSE`, `_INSERT_PORT_IFS`, `_IFS_COLORS`, `START_PRINT`) read both and merge behaviour, not text.
   - Where bambufy HEAD *removed* something the lessWaste delta still relies on (e.g. auto color mapping was disabled upstream), decide explicitly and record it.
3. Regenerate the other language configs via the existing translate scripts (bambufy `.po`, lessWaste CSV). Two translation toolchains exist — reconcile into one; new strings for lessWaste-only features need entries in every language (fallback: English).
4. One `install.sh` that migrates *both* legacy variable prefixes to the unified one, keeps bambufy's `VERSION` reinstall mechanism, and refuses to install alongside the original `bambufy`/`lesswaste` plugins.
5. Docs: one README, one machine-G-code doc (Orca + Bambu Studio), credits to all authors.

**Verification (no hardware):**
- Script that fails on: duplicate `[gcode_macro X]` sections, `SET_GCODE_VARIABLE`/`_IFS_VARS` references to undefined variables, macros called but not defined, unbalanced Jinja blocks.
- Diff macro inventory against the union of the two originals; every removal must be justified in the spec/changelog.
- All language configs have the same macro set as `en`.
- Hardware smoke test (user): boot, `_IFS_COLORS` dialog opens, a 2-color print runs, one lessWaste feature (channel swap) works.

## Phase 2 — QuickSwap (direction only; own spec later)

**Approach A (approved):** keep `quickswap.py` as a Klipper extra. The unified `_T` / `_INSERT_PORT_IFS` / `_IFS_UNLOAD` path calls `_QS_CHANGE_FILAMENT` when a "quick swap" option is on; the original bambufy path stays as the fallback. Rejected: rewriting in Jinja (cannot do async IFS / parallel motion), and handing `_A_CHANGE_FILAMENT` back to Z-Mod (loses slicer-controlled purge).

**Hypothesis to verify first:** because `zmod_ifs` and `filament.json` still exist under bambufy, the "adapter" may be nearly empty — QuickSwap can keep reading per-filament values from `get_prutok_config`. The real work is **state consistency** between the two models:
- bambufy `_IFS_VARS.extruder_port` / `current_tool` / `_NOPOOP` state ↔ QuickSwap's `get_current_channel_from_config()` and `use_trash_on_print`.
- Who owns purge: bambufy = slicer G-code (`_GOTO_TRASH`, `_SBROS_TRASH`); QuickSwap = built into the swap.
- Backup channels / virtual channels (lessWaste) vs QuickSwap's own `_qs_get_switchover` mapping — must be one mechanism, not two.
- QuickSwap's calibrations write to `filament.json` by hand; bambufy uses its own `_IFS_VARS` timings — pick one source of truth per value.
- Compatibility floor inherited from QuickSwap: Z-Mod ≥ 1.7.3-79, Klipper 12.
- **Klipper 13:** QuickSwap says only "not tested" (no commit or code mentions a break). Checked upstream Klipper v0.12.0 vs v0.13.0: every Klipper API `quickswap.py` uses (`gcode_handlers`, `register_command`, `run_script_from_command`, `toolhead.max_velocity`, `get_kinematics().max_z_velocity`, `gcode_move.get_status`) is unchanged, and its command names pass v0.13's new name validation. Real risks are elsewhere: (a) private Z-Mod attributes it pokes (`zmod_ifs._command`, `_command_id`, `_command_lock`); (b) timing — lessWaste recommends Klipper 12 to avoid "timer too close", and QuickSwap's async IFS + parallel moves are timing-sensitive; (c) Z-Mod's Klipper 13 build may differ from upstream v0.13.0 (not checked). Default: target Klipper 12; treat 13 as a Phase 2 test item.

**Phase 2 delivery includes** a hardware test plan for the user: calibrations first, then a short multi-color print with few swaps, comparing swap time with the Phase 1 baseline.
